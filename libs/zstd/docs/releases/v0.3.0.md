# mojo-zstd v0.3.0

**Released:** 2026-11-26 · **Commit:** tag `zstd-v0.3.0` · **Previous:** [v0.2.0](v0.2.0.md)

## What it does

<!-- Stable description of the program. Carried forward from the previous note; edit only when the product itself changes.
     3 to 6 lines: what it is, who uses it, where it runs (URL/port/binary), how to start it. -->
zstd and lz4 frame compression for Mojo, in pure Mojo: one-shot `compress`/`decompress`, and
streaming zstd files or buffers through a 128 KiB window. No C library, no foreign calls, no linker flag.

## Highlights

<!-- 1 to 5 bullets a user would notice. Lead with the benefit, not the implementation. -->
- Much faster at level 3 (issue #31): compress runs at 0.76 to 0.96x libzstd's speed and decompress at 0.64 to 0.70x
  on random, repetitive, binary, source and JSON input. In v0.2.0 the issue measured compress 1.3 to 6.8x and
  decompress 1.6 to 4.6x slower than libzstd.
- Same output: compressed sizes are byte-count identical to v0.2.0 at every level, and decoding still accepts and
  rejects exactly what libzstd 1.5.7 does.
- Higher levels got faster too: level 9 49 -> 42 ms and level 19 2750 -> 2601 ms on 4 MiB of text.

## Changes

### Added
- `scripts/bench31.sh` and `tests/bench31.mojo`: level-3 throughput of five inputs against `zstd -b3 --single-thread`.
### Changed
- Decoder: overlapping matches, literals and short matches copy 16 bytes per step; the four Huffman streams decode
  side by side; `decompress` reserves the frame's declared content size in one step (capped at 64 MiB past what is
  decoded, so a lying header stays cheap) instead of growing by doubling.
- Encoder: flat literals go raw without building a Huffman table (libzstd's heuristic); match-free flat blocks skip
  entropy work; sequences are stored with 16-byte literal copies; block-split fingerprints use raw pointers.
### Fixed
- Builds on Mojo 1.3 nightly (interior origins, `ZstdReader` / `ZstdWriter`).

## Known limits

- Decompression is still 0.64 to 0.70x libzstd: the sequence loop, double-symbol Huffman tables and the dfast match
  finder are the open items.
- Peak RSS of `decompress` on 32 MiB is 6 MB above v0.2.0 (one-step reservation of the declared size).
- `zstd.decompress` allocates a new output per call; `zstd -b` reuses its buffer, so part of the remaining decode gap
  is allocation and page faults.
- Not covered: dictionaries, multithreading, long-distance matching, the lz4 block format, lz4 levels.
