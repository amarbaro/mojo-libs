# mojo-zstd v0.4.1

**Released:** 2026-11-28 · **Commit:** tag `zstd-v0.4.1` · **Previous:** [v0.4.0](v0.4.0.md)

## What it does

zstd and lz4 frame compression for Mojo, in pure Mojo: one-shot `compress`/`decompress`, and
streaming zstd files or buffers through a 128 KiB window. No C library, no foreign calls, no linker flag.

## Highlights

- Level 9 compresses 0.86 to 1.06x libzstd 1.5.7's speed (v0.4.0: 0.17 to 0.63x); random bytes 646 -> 3615 MB/s (issue #34).
- Levels 5 to 12 use libzstd's row match finder: JSON at level 12 goes 9 -> 35 MB/s.
- Level-9 frames are within 0.1% of libzstd's size (v0.4.0: up to 3.8% larger on JSON).
- `ZstdReader` no longer fails when the checksum arrives in a later read than the last block (issue #32).

## Changes

### Changed
- Greedy, lazy and lazy2 parsers (levels 5 to 12, window over 16 KiB) use a row match finder: tag bytes compared by
  SIMD, hashes computed 8 ahead with row prefetch, cache-line rows.
- After 2 KiB without a match only searched positions enter the match tables, as libzstd's lazy skipping does.
- `compress()` returns a list sized to the frame, not to the input (issue #33).
### Fixed
- The lazy parsers charged a held repeat-offset match a full offset's cost; libzstd charges none. Level-9 frames
  shrink 2.2% (executable) and 3.2% (JSON).
- `ZstdReader` raised "truncated input" when the frame checksum was split from the last block by its input buffer.

## Known limits

- Level 9 on real data is 10 to 14% behind libzstd: the row search waits on cache misses for match candidates.
- Level 3 on real data is still 0.71 to 0.76x libzstd.
- Smaller level-9 frames carry more sequences: the executable decodes about 8% slower per byte than v0.4.0's frame.
- Not measured on arm64 or on the Mojo 1.3 nightly.
- libzstd 1.6.0 rejects 32 corrupted golden frames that 1.5.7 and this decoder accept; the gate stays on 1.5.7.
